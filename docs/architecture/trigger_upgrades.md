"可观测、可判定"的触发条件，命中才立项，未命中不投入。本文是唯一的升级决策入口——

## 1. Redis（BP-V2-A01）

- **触发条件**（任一命中）：
  1. 引入 Celery（升级项 2）时一并进场（broker 复用）；
  2. 出现真实的多进程/多实例部署（>1 个 backend 实例），进程内 cachetools 缓存命中率
     明显下降或数据不一致；
  3. 外部数据源限流需要跨进程共享配额（当前采集限流是进程内问题，单进程够用）。
- **方案要点**：redis-compose 服务 + 环境变量开关（`cache_backend=redis`）；cachetools
  与 Redis 双实现共存，按开关切换；会话/JWT 无状态不受影响，暂不迁。
- **验收标准**：切换后因子/行情接口 P95 不劣化；重启后缓存热身 < 1 分钟；单实例回退开关可用。
- **预估规模**：M（2~3 天，含双实现改造与压测对比）。

## 2. Celery + Redis 任务队列（BP-V2-A02）

- **触发条件**（任一命中）：
  1. 任务需要**跨重启续跑**成为硬需求（当前 V2.5 进程内重试 + 次日兜底已覆盖日频场景）；
  2. 后台并发成为常态——同时间段需要并行执行 ≥3 个长任务且互相排队造成交付延迟
     （当前单 worker 长任务池串行是刻意设计：修复/重灌同源不可叠加）；
  3. 任务延迟要求从"分钟级"进入"秒级"（事件驱动形态）。
- **方案要点**：Celery worker 独立容器；`sa_pipeline_step` 状态语义直接映射为任务消息
  （step 记录结构已预留：step_key/attempts/status）；APScheduler 保留为 beat 层；
  `sa_admin_task_log` 保留为任务历史。`pipeline_enabled` 开关在切换期作降级通道。
- **验收标准**：日管线全链路在 Celery 上跑通一周无漂移；重启后 running 任务自动恢复或明确失败；
  长任务并发 ≤2（同源限流仍在）。
- **预估规模**：L（4~5 天，含双跑灰度）。

## 3. ClickHouse / MySQL 分区（BP-V2-A03）

- **触发条件**（任一命中）：
  1. 分钟 K 线入库立项（数据量从 ~650 万行/5 年跳到 ~15 亿行/年）；
  2. K 线查询体感变慢：行情/因子页面接口 P95 > 3s（当前 MySQL 索引下全市场 5 年查询
     亚秒级）；先做 MySQL 按月分区，仍慢再评估 ClickHouse；
  3. 单表超过 ~5000 万行且备份/DDL 窗口影响日常调度。
- **方案要点**：第一阶梯 MySQL 分区（按 trade_date 月分区，`alter table ... partition by`，
  对应用透明）；第二阶梯 ClickHouse 只做 K 线分析副本（写双轨），MySQL 保留业务事实表。
- **验收标准**：分区切换后全部查询行为不变（回归对比）；ClickHouse 路径因子面板构建
  提速可量化；回退路径 = 摘除副本读路由。
- **预估规模**：分区 M（2 天）；ClickHouse L（5 天+）。

## 4. 微服务拆分（BP-V2-A04）——结论"不做"

- **触发条件**（重启评估，任一命中才重新讨论）：
  1. 出现第二个使用者/团队需要独立演进某模块（当前单人使用不存在）；
  2. 某模块的资源形态与其他模块严重冲突（如 AI 推理需要 GPU 独占节点）；
  3. 单体部署的发布耦合造成实际事故（某模块发版拖垮整体，月均 ≥1 次）。
- **方案要点**（若重启）：按 data / market / strategy 边界拆；先抽 library 再拆服务；
  拆分代价评估必须包含"单人运维 N 个服务"的成本。
- **验收标准**：N/A（未触发不设计）。
- **预估规模**：XL（数周，且运维成本永久 +1）。

## 5. K8s / 部署规范化（BP-V2-A05）——不做

- **触发条件**：多服务多机部署成为现实（当前 docker-compose 双容器 + 外部 RDS 稳定运行）。
  健康检查/重启策略在 compose 层补齐即可，不引入编排系统。
- **注记**：原保留项「DB 备份 + 恢复演练」已于 2026-09-09 立项评审移出平台侧
  （见附录 A）；K8s 本体无保留项。
- **预估规模**：N/A。

## 6. ES 全文检索（BP-V2-007）

- **触发条件**（任一命中）：
  1. MySQL ngram 前缀检索的个股/资讯搜索 P95 > 1s 或召回明显不足（可观测：搜索无结果率）；
  2. 检索数据源扩展到研报/公告全文（BP-V3 T5.5 RAG 扩容立项时一并评估）。
- **方案要点**：ES 单节点容器 + canal/双写同步 stock/news 表；检索 API 保持现有契约。
- **验收标准**：搜索无结果率下降可量化；同步延迟 < 5 分钟；MySQL 降级路径可用。
- **预估规模**：M（2~3 天）。

## 附录 B：当前形态基线（判断触发的参照）

- 部署：单机 docker-compose（backend + frontend），DB 为外部阿里云 RDS；
- 调度：APScheduler 进程内，18 个 cron job + 2 个条件轮询 tick，线程池 10；
- 数据量：全市场 5 年日 K ≈ 650 万行；日增量 ≈ 4,600 行；
- 长任务：单 worker 串行池（防同源叠加），V2.5 起有管线步骤级重试与当日告警；
- 使用者：1 人；查询 QPS：< 1。
